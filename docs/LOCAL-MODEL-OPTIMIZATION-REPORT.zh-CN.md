# 本机 Strata 模型上下文、参数与优化报告

**检查日期：2026-10-17**  
**对象：Qwen3.8-Flash-Next / Unsloth UD-IQ4_XS，Strata 0.1.44.1，Windows + CUDA 12**

> 本报告依据当前配置、正在运行的本地 HTTP 服务、启动日志、GGUF 元数据及本地源码编写。此次只读检查并生成文档，没有修改运行配置、重启模型、更新引擎或发起额外推理测试。所有优化值均为待验证建议，不代表已经取得性能提升。

## 1. 结论：现在最大上下文是多少？

### 1.1 三个不同的“最大值”

| 层次 | 数值 | 对本机意味着什么 |
|---|---:|---|
| **当前服务实际生效上限** | **131,072 tokens，即 128K** | `/health`、`/v1/models` 和 `/metrics` 均确认；现在的客户端必须按这个限制发送请求 |
| **模型元数据中的原生上下文** | **262,144 tokens，即 256K** | 本地 GGUF 的 `qwen4exp.context_length=262144`；可作为下一档验证目标，不等于本机已经验证可以稳定跑满 |
| **超过原生长度的实验扩展** | 384K、512K、1M 等 | Strata 支持 YaRN 等 RoPE 缩放；项目文档记录其他硬件和量化的长上下文实验，不是这台 2080 Ti 的可用性或质量保证 |

**建议：先稳定当前 128K 的显存余量，再试 256K。不要直接把“最大上下文”设成 1M。**

当前硬件与实际长文本负载的稳定上限，必须通过逐级加载、长提示词、生成和检索准确率测试才能确定，不能仅由“96 GB 内存”推导出来。

源码中的整数边界也不是模型能力：`src/program/generate.cpp:2647` 对上下文做了接近 `2^31` 的索引保护，它不表示能运行几十亿 token。1M 同样只是已有实验档位，不是已确认的引擎硬上限。

### 1.2 上下文不是全部都能拿来输入

当前服务的计算规则为：

```text
完整输入 token 数 + 本次最大生成 token 数 + 8 <= max_context
```

完整输入包括系统提示、历史对话、工具定义、工具结果和模板标记。思考输出也需要消耗生成预算/上下文，不能把它当成免费空间。Token 不等于汉字数，代码和中英文混合文本的比例尤其不固定。

| 上下文 | 预留输出 | 最多完整输入 token 数 |
|---:|---:|---:|
| 131,072 | 8,192 | 122,872 |
| 131,072 | 16,384 | 114,680 |
| 131,072 | 32,768 | 98,296 |
| 262,144 | 8,192 | 253,944 |
| 262,144 | 16,384 | 245,752 |

这些是服务端公式上限，不是推荐贴边使用的目标。客户端还应为下一轮工具结果预留空间；长会话应提前压缩或总结。

设置 `fit_max_tokens=true` 只能缩短输出额度，**不会增加上下文，不会自动截断过长输入，也不等于自动总结历史**。

## 3. 主要瓶颈：显存余量，而不是“模型装不进 96 GB”

### 3.1 优先级最高：Windows 显存换页风险

实际日志包含：

```text
413 MiB of VRAM free with everything loaded
WARNING: only 423 MiB of VRAM free at the start of this request (below 1024 MiB)
Add --vram-reserve-mib 1344 to the config's args
capturing the 5-token window (51 MiB of VRAM free)
```

检查时 `nvidia-smi` 也只报告约 **577 MiB free**。这些数字是不同阶段的快照，不能混为同一时刻。

这说明：模型虽然成功加载，也能达到短请求 22.8 tok/s，但捕获不同验证窗口时显存可能非常接近耗尽。Windows WDDM 发生 GPU 内存迁移后，可能出现：

- 输出突然降到几 token/s；
- GPU 利用率很高，但吞吐很低；
- 长请求卡住或显著抖动；
- 浏览器/桌面/其他 GPU 程序介入后不稳定。

**第一项建议：把界面的 `vram_reserve_mib` 设置为 `1536`，保存并完整重启模型，再测。**

- 1344 是当前日志给出的修复参考；1536 是本报告建议的第一档试验值，留少量额外余量。
- 若仍低于约 1 GiB 或反复出现警告，再试 2048。
- 目标是负载期间不持续贴近零显存；不是机械要求所有时刻都完全不波动。
- 代价是 GPU 专家缓存可能缩小，正常情况下速度也可能略降；若原来发生换页，反而可能显著更稳定。
- 预留值不是“保证实际空闲显存始终等于该值”，仍需观察验证窗口和其他程序的占用。
- 不建议关闭预留或强行增大 `--expert-cache`。

### 3.2 内存有余量，但锁页/提交能力已经影响了执行路径

日志显示：

```text
loaded 55.43 GiB at 4.55 GiB/s
cudaHostRegister of the whole arena FAILED (out of memory)
39 slices pinned (44 GiB)
large pages refused ... VirtualAlloc error 1314; using 4 KB pages
Windows commit: 25.3 GiB left of a 127.0 GiB limit (RAM + page file)
prefill: the CPU share is off ... RAM is short; the GPU streams every expert
```

如何理解：

1. **55.43 GiB 专家已加载到 RAM**。当前配置没有 `--resident-budget-gib` / `--mmap-experts`，不是之前 48 GB 条件下必然依赖 SSD 的判断。
2. 整块 pinned 注册失败后已有部分锁页回退，程序仍能运行；不能把这一行直接等同于模型加载失败。
3. “还有约 20 GiB 空闲内存”不保证大块 pinned 分配成功。Windows 提交限制、锁页、已有分配和驱动状态是不同约束。
4. 启动时大页申请失败并回退 4 KB 页，不是致命错误；涉及系统权限的优化不宜作为第一步。
5. 短请求记录没有专家文件读取，不代表以后所有长请求都不会碰磁盘，也不能据此排除 Windows 页面迁移。

建议顺序：

- 关闭不用的大内存应用、虚拟机和其他模型服务。
- 保留 Windows 分页文件，不要为了“全内存运行”禁用它。
- 若确实出现提交容量不足，再检查分页文件位置和系统管理策略；扩大分页文件不等于让 SSD 达到 RAM 速度。
- 重启后观察 CPU prefill share 是否恢复、pin 回退是否变化；目前不保证单靠清理应用能解决。
- 不直接开启管理员权限或调整“锁定内存页”策略；确需尝试时单独备份、授权和对照测试。

### 3.3 CPU、内存带宽和 PCIe

3700X 是较早的 Zen 2 平台，当前内存报告 2400 速率，专家缓存未命中的部分可能受 CPU/内存带宽影响。软件参数无法把这台机器变成现代高带宽工作站。

当前 PCIe 已是 Gen 3 ×16，没有证据表明需要调整 PCIe 插槽。**不建议直接强制 `pcie_frac=1`，也不建议按逻辑线程数设置 16 个 workers。** CPU 和 GPU 分工要测。

## 4. 你贴出的 Model settings：逐项说明和推荐值

### 4.1 `default` 到底是什么意思？

`default` / 空白通常表示该键没有写入运行配置，使用程序默认行为，不是所有项目都自动优化。

当前 `/config` 返回你列出的 15 个设置项均为 `null`，与界面一致。

- Settings 保存的是模型 JSON，不是仅针对当前浏览器标签页。
- 保存后，**完整关闭并重新启动 Strata** 才使用新配置；仅刷新网页不够。
- 请求显式携带的采样参数优先于全局默认。
- Settings 保存实现会生成 `strata-unsloth-ud-iq4_xs.json.bak`，但该备份会在下一次保存时被覆盖；重要调整前另外做带时间戳备份。

### 4.2 完整设置表

| 设置 | 默认 / 实际含义 | 对这台机器的建议 | 注意事项 |
|---|---|---|---|
| `sampling.temperature` | 未指定 sampling 且请求也没指定时为 greedy；`0` 取最高概率 token | 性能基线保留默认或明确 `0`；日常问答可试 `0.6`，创作可试 `0.8` | 这是输出策略，不是直接提高硬件速度；没有模型任务测试就不能称某值“最佳” |
| `sampling.top_p` | 不写则交给当前采样路径默认；设置范围 `0 < p <= 1` | 采样模式先试 `0.95` | 只在采样时有意义；greedy 下调它不能变得更聪明 |
| `sampling.top_k` | Settings 允许整数 1–64；引擎采样候选数最多 64 | 采样模式先试 `20` | 不照搬其他引擎的 `100`、`200` 或配置字段里的 `0`；Settings 会校验 |
| `sampling.min_p` | 范围 0–1，相对概率过滤 | 第一轮保持空白或显式 `0` | 同时收紧 top_p/top_k/min_p 容易过度过滤；它不是 `--spec-min-p` |
| `reasoning_budget_tokens` | 空白/0 不额外限制思考 | 日常可试 `4096`；复杂任务 8192 或不限制 | 减少无效长思考，不增加上下文；不是最终答案字数限制；请求可覆盖，见下文 |
| `fit_max_tokens` | 默认 false，输入加请求输出超过窗口时返回 400 | 个人工具接入建议 true；严格测试可保留 false | 只能压缩输出配额；可能导致答案更早结束，要检查 `finish_reason` / 停止原因 |
| `anthropic_thinking` | 默认 `model`，Anthropic 请求没要求思考时也按模型默认思考 | 延迟优先可试 `on_request` | 只作用于对应兼容接口；不是全局关闭 OpenAI 请求的 thinking；复杂任务需客户端明确请求 |
| `effort_position` | 默认 `start`，非默认 reasoning effort 放在前部 | 经常切换 effort 的工具可试 `end`；否则保持默认 | 有助于减少因 effort 改变破坏前缀缓存的情况，不保证所有请求都命中缓存 |
| `aliases` | 默认无额外别名 | 能用真实模型名就留空；必要时加 `local-qwen` | 别名只是路由和列出名称，不会改变模型能力、上下文或变成别的厂商模型 |
| `idle_unload_s` | 默认 0，不因空闲自动卸载 | 持续使用留 0；只偶尔使用可试 1800 | 自动卸载释放资源，但下次请求有冷启动；不是推理加速 |
| `lazy_load` | 默认 false，启动时加载模型 | 常用服务留 false | true 可快速启动服务外壳，但第一次请求才付加载成本；仅文本模式 |
| `engine_silence_s` | 默认 300 秒；引擎连续没有输出时终止请求 | 保持 300；确认是正常长步骤且无换页后才试 600 | 不是整个请求总时限；设置 0 会无限等待，不能用来掩盖显存卡死 |
| `api_monitor` | 默认 false；开启后在内存保存最近 100 条请求的提示和回答 | 平时 false，短期排错 true | 含隐私/代码/工具结果；长上下文占内存，别长期无条件开启 |
| `open_browser` | 当前 BAT 带 `--open`，未显式禁用时就打开页面 | 按习惯；纯 API 服务可 false | 只是界面行为，不提高生成吞吐 |
| `vram_reserve_mib` | 默认 700；界面实际写入 `args` 中的 `--vram-reserve-mib` | **第一步试 1536，必要时 2048** | 当前最有证据支持的优化；不是写同名顶层 JSON 字段 |

### 4.3 两个容易被界面描述误导的地方

**思考预算不是不可绕过的全局硬上限。**

`serve/server.py:3209` 的实际逻辑优先读取请求 `reasoning_budget_tokens`，没有才用配置默认；请求传 0 可以取消配置默认预算。因此界面的“every request”应理解为默认作用于未自行指定预算的请求，而非强制策略。不要用它代替多用户配额控制。

**默认温度为 0 不代表每个客户端现在都用 0。**

浏览器或接入工具可能发送自己的 temperature/top_p 等参数。若要做 A/B 测速，应在相同请求中显式固定采样参数，而不是仅比较界面显示的 default。

### 4.4 可用的设置组合

以下是起始实验组合，不是已经测得的最佳设置。

#### A. 第一轮性能基线：只改一个参数

```text
vram_reserve_mib = 1536
其余保持当前值
context = 131072
kv = int8
kv-resident = 32768
```

这样才能判断显存预留的真实影响，不要同时修改 temperature、思考预算和上下文。

#### B. 日常交互 / 工具调用

在 A 验证之后，按需逐项设置：

```text
sampling.temperature = 0.6
sampling.top_p = 0.95
sampling.top_k = 20
sampling.min_p = 0
reasoning_budget_tokens = 4096
fit_max_tokens = true
anthropic_thinking = on_request
idle_unload_s = 0
lazy_load = false
engine_silence_s = 300
api_monitor = false
```

复杂数学、规划、长代码任务可提高或取消思考预算，并显式要求 thinking；不能为了少输出 token 就认为质量更好。

#### C. 严格对照 / 可复现测试

- 请求显式设置 `temperature=0`。
- 固定提示词、max_tokens、thinking 模式和客户端版本。
- `STRATA_ROUTE_TAIL_SKIP=0` 保持不变。
- 除被测参数外其他项不变。
- Greedy 也不保证跨引擎版本、并行路径、不同缓存布局绝对逐字相同。

## 5. 如何提升到 256K：推荐实施方式

### 5.1 先满足前提

1. 先完成 1536 MiB 显存预留的 128K 基线测试。
2. 完整退出当前 Strata，确认没有第二个模型占用 GPU/8080。
3. 备份 JSON。
4. 确认仍有合理的可用 RAM 和 Windows 提交空间。
5. 仅提高上下文，先不要把 KV 换成 4-bit，也不要调整专家缓存。

### 5.2 JSON 中的最小修改

在当前 JSON 的 `args` 数组里，**替换已有的**：

```json
"--max-context", "131072"
```

为：

```json
"--max-context", "262144"
```

保留：

```json
"--kv", "int8",
"--kv-resident", "32768"
```

并确保 `args` 中仅有一组显存预留项：

```json
"--vram-reserve-mib", "1536"
```

上面都是数组片段，**不是整个 JSON 文件**。不能把整份配置覆盖成这些片段；原有 exe、pack、native、tokenizer、MTP、env 等字段均需保留。不要重复追加同一个 flag。

**256K 位于本地元数据原生范围内，不需要为了这个档位强行加 YaRN。**

重新双击 `run-unsloth-ud-iq4_xs.bat`，检查 `/health` 的 `max_context` 是否变为 262144。服务成功启动仅表示分配/初始化通过，还需要长输入验证。

### 5.3 为什么优先建议改现有 JSON，而不是重新安装

当前新模型已经完成准备，不需要再次下载或打包。当前 `START-HERE.bat` 的本地配置路径仍含 `--context 131072`：

- 普通启动已配置模型不会把上下文改回去。
- 但在 `SETUP.bat` 菜单里重新准备模型，可能再次写入 131072。
- 手动优化后，若重跑安装/配置流程，应复查 JSON。
- 安装器生成并覆盖 `run-<model>.bat` 属正常行为，启动命令的权威来源是它实际读取的 JSON。

### 5.4 扩展档位及内存估算

当前 int8 KV 日志为 128K 对应约 **1.55 GiB pinned RAM**。按本模型 12 个 QSA 层、每位置 1056 bytes 粗估：

```text
KV RAM 约等于 context × 12 × 1056 bytes
```

| 上下文档位 | tokens | KV 主存粗估 | RoPE 处理 | 推荐级别 |
|---|---:|---:|---|---|
| 64K | 65,536 | 0.77 GiB | 原生 | 日常较短会话可对照，不保证比 128K 明显更快 |
| **128K** | **131,072** | **1.55 GiB** | 原生 | 当前正在运行，先做稳定性优化 |
| **256K** | **262,144** | **3.09 GiB** | 原生 | 下一档优先测试 |
| 384K | 393,216 | 4.64 GiB | `yarn`，factor 1.5 | 实验 |
| 512K | 524,288 | 6.19 GiB | `yarn`，factor 2 | 实验，长文准确率需单独验证 |
| 1M | 1,048,576 | 12.38 GiB | `yarn`，factor 4 | 不推荐本机作为默认配置 |

估算只包括主要 KV 主存副本，不包括：GPU KV 工作集、RoPE 表、状态/工作缓冲、请求 token 数组、CPU prefill 缓冲、操作系统、前缀缓存及客户端程序。不能把表中数字当成模型总内存。

从 128K 到 256K，主要 KV 主存估算增加约 1.55 GiB，当前 96 GB RAM 看起来有尝试空间；但 pinned 分配、WDDM 显存余量及长提示词缓冲仍可能先成为瓶颈。

### 5.5 超过 256K 的实验片段

例如 **512K** 需要一起考虑：

```json
"--max-context", "524288",
"--rope-scaling", "yarn",
"--rope-scale", "2"
```

- 仅作为实验配置示例，本报告没有应用。
- 不要保留重复的 max-context 或旧的 rope-scale。
- RoPE 缩放固定于整次运行，必须重启；不能在一个现有 KV 缓存中混用。
- 缩放会影响整个上下文内的计算，不是只影响超过 256K 的部分。
- 必须检验短任务回归、长文检索、多文档推理和答案依据，而不是只看能否输入成功。

## 6. 优化项优先级与取舍

| 优先级 | 动作 | 预期收益 | 代价 / 风险 | 验证方式 |
|---|---|---|---|---|
| P0 | 显存预留 1536，必要时 2048 | 降低 WDDM 换页/卡顿风险 | 少一些缓存专家，未换页时也可能变慢 | 显存低水位、警告、相同请求吞吐 |
| P0 | 清理其他 GPU/RAM 占用 | 给锁页、验证窗口和长请求留空间 | 需要关闭应用 | 可用 RAM、commit、pin 日志 |
| P1 | 正确配置客户端 context/output，开启适当历史压缩 | 减少 400、重复传输和无效长输入 | 过早压缩可能丢信息 | 请求 token 数、任务成功率 |
| P1 | 合理限制 thinking | 降低响应时间和生成成本 | 推理复杂任务可能变差 | 总延迟、正确率、思考/答案 token |
| P1 | 保持提示词前缀稳定 | 提高复用，减少 prefill | 动态系统提示会破坏复用 | `reused` / `prompt_read` |
| P1 | 128K → 256K 逐级验证 | 容纳更长历史/文档 | 更高资源和预填充成本；不是提速 | 长文准确率、尾延迟、显存/提交峰值 |
| P2 | 同机比较 IQ3_S / IQ2_XS | 较小专家通常更容易缓存，可能更快 | 量化质量与任务表现变化；需实测 | 同样提示与输出设置的中位数 |
| P2 | 官方 `--calibrate` | 按本机测 CPU/PCIe/MTP/缓存适配 | 耗时、反复重载，并可能检查更新 | 备份后对照，保留明确收益 |
| P3 | 调整 KV 驻留、prefill chunk | 平衡缓存专家、传输和缓冲 | 短/长任务可能相反 | 分长度负载测试 |
| P3 | 尝试 `k8v4` KV | 节省部分 KV 空间 | 数值/质量变化，收益不保证 | 检索+推理质量与吞吐 |
| P4 | 近似 tail skip、全 q4 KV、硬件/BIOS 调整 | 可能进一步提速 | 质量或系统稳定性风险更高 | 独立实验，不混入稳定基线 |

### 6.1 模型切换建议

- **UD-IQ4_XS：** 当前已能运行，适合保留为质量优先候选。更高位宽通常有利于减少量化损失，但不保证每个任务都胜出。
- **IQ3_S：** 值得作为速度/质量平衡候选进行同机对照。
- **IQ2_XS：** 值得作为低资源和交互速度候选；应检查长文、工具调用和代码任务的准确率。
- **Orca IQ2_XXS：** 不只是位宽变化，还涉及不同模型版本/微调与自定义 embedding 处理，不能把其所有行为差异都归因于量化。

本报告没有跑四模型横评，不提供虚构的“换成某模型一定达到多少 tok/s”。

### 6.2 KV 相关调优

**优先保留 `int8 + kv-resident 32768`。** 当前短请求 KV 读取命中显存达到 99.06%，没有证据表明它是此请求的主要瓶颈。

可后续单独试验：

1. `--kv-resident 20480`：源码支持的最小非零驻留档，释放部分 GPU KV 空间但可能增加 RAM→GPU 读取；按上下文长度做 A/B。
2. `--kv k8v4`：项目文档给出相对 int8 约 23% 的 KV 内存节约，结果来自其他硬件/模型，不等于本机整体速度提高 23%。
3. `--kv q4_0`：内存更省，但项目已报告长文质量损失；不建议作为当前质量优先配置的第一项改动。

`--kv-resident` 是存放位置/工作集控制，`--kv` 是数值表示，两者不是同一个参数。不要关闭 KV streaming 后把整个长上下文 KV 都塞进这张已经紧张的 GPU。

### 6.3 MTP 和 prefill

- 当前 `52/75` 的草稿接受只是单次观测；没有关闭 MTP 的对照，不能据此量化实际加速倍数。
- 保留 `--spec 4` / `--spec-min-p 0.5` 作为起点；更大窗口需要更多缓冲，不适合在仅几十 MiB 余量时盲目增加。
- 当前 `--prefill auto` 实际为 8192。日志建议的 `auto:8192` 在此次运行不一定会进一步缩小，因为当前已是该大小。
- 若优化显存预留后仍有 prompt 内存问题，可单独试 `--prefill auto:4096`，但可能降低长提示词吞吐。
- 不照搬 5090 的 32768 分块或多并发参数；本机单请求就已接近显存边界。

### 6.4 校准命令：有副作用，建议安排空闲时间

在 Strata 目录的 CMD 中，明确选择当前已安装模型：

```bat
START-HERE.bat --calibrate --family unsloth --model UD-IQ4_XS --no-start
```

这不是本报告已执行的命令。执行前：

1. 停止现有服务，保存配置及当前 `engine-cuda12\BUILD.json` 版本信息。
2. 预留至少几十分钟；旧卡或重载可能更久。
3. **本地 `setup.py:5897` 的校准路径会调用 `update_installed_engine`，可能检查/进行引擎更新或访问网络。** 如要严格固定 0.1.44.1 做实验，应先解决版本隔离，而不是直接跑此命令。
4. `--no-start` 是结束后不进入常驻服务，不表示校准过程中不会加载模型/使用 GPU。
5. 重点测 `pcie-frac`、`spec-min-p`、`pool-workers` 和缓存适配参数。项目校准以超过 3% 的提升作为保留判断之一，但仍要对自己的真实任务复测。

### 6.5 硬件升级方向

不提供无测量依据的购买收益承诺。按当前瓶颈，优先考虑：

1. **更大显存且带宽/算力更强的 GPU**：可能同时容纳更多专家、KV 和验证缓冲。单纯 22 → 24 GiB 只增加约 2 GiB，不应预期模型突然全驻留；完整专家仍有约 55 GiB。
2. **更高内存带宽的平台 / 合理内存布局**：CPU 专家路径可能获益。现有四条混容量 2400 配置应先检查通道、稳定性及主板支持，不建议直接指导超频。
3. **更多 RAM**：有利于多应用、长上下文和缓冲；当前已 96 GB，不是第一优先级。须先确认主板/CPU 的支持上限。
4. **SSD**：当前 D 盘已 NVMe，短请求没有专家文件读取；升级 SSD 不应排在显存稳定性之前。

### 7.3 超时不要只改一个层级

长文处理需同时关注客户端连接/读取超时、代理超时、`engine_silence_s` 和模型实际进度。服务持续有进度却被客户端超时断开，与引擎完全卡死是两个问题。

优先看日志和显存。如果实际在 WDDM 换页/停滞，单纯把 `engine_silence_s` 改成 0 只会把问题变成无限等待。

## 9. 建议的测试矩阵与验收标准

### 9.1 分阶段，不同时改所有东西

| 阶段 | 配置变化 | 主要验证 |
|---|---|---|
| 基线 | 当前 128K / int8 / reserve 默认 | 记录现状，不长时间反复制造显存压力 |
| A | 仅 reserve=1536 | 显存稳定性、短请求速度 |
| B | 若 A 仍紧张，仅 reserve=2048 | 余量与缓存缩小的取舍 |
| C | 在稳定 A/B 上改为 256K | 启动、8K/32K/64K/128K/接近窗口边界的长请求 |
| D | 单独尝试 IQ3_S | 相同任务速度/质量对照 |
| E | 再考虑 k8v4 / prefill / calibration | 精细调优，保留可回滚基线 |

### 9.2 每组记录什么

- 冷启动耗时与 warm-up 后的速度分别记录。
- 输入 token 数、实际输出 token 数、thinking 模式和采样参数。
- TTFT、prefill tokens/s、decode tokens/s、总延迟。
- `prompt_read` / `reused`，避免把缓存命中误当纯计算提速。
- MTP 接受比例、GPU 专家命中率、专家文件读取量。
- 显存最低余量、系统可用 RAM 和 Windows commit 余量。
- OOM、超时、停止原因、异常重复或答案截断。
- 相同提示词重复至少 3–5 次，比较中位数；冷缓存与热缓存分开。

### 9.3 长上下文质量测试

不要只发一大段重复字符或只做一次“针藏在草堆”检索。

建议组合：

1. 在文档开头、中间、末尾分别放可核验事实，要求引用原文定位。
2. 多文档事实交叉，加入相近但不相同的干扰信息。
3. 长代码任务要求跨文件修改点/调用链说明，并核对来源。
4. 预留足够输出预算，避免因截断误判模型不会回答。
5. 扩展 YaRN 后同样跑短任务回归，不能只检查长任务。

### 9.4 “优化有效”的判定

- **稳定性：** 不再出现显存贴近零导致的持续卡顿；长请求能完成。
- **性能：** 同任务、同输出策略、多次运行的中位数有可重复改善，而不是仅短一次快了。
- **质量：** 正确率、引用准确性、工具格式遵循没有不可接受的下降。
- **资源：** 不以持续页面文件读写、桌面明显卡顿或更多失败换取表面 tokens/s。
